## 4. TypeScript/Bun decision

The Wiki's original rationale is type safety, maintainability, inspectable shared contracts and conceptual alignment with typed Ontology definition/query/action surfaces—not language percentage or unverified performance.

- Prefer strict TS and the already installed pinned Bun for new or genuinely consolidated portable operational meaning, decision rules and appropriate local contract tests. Keep domain identity/provenance language-neutral and shared pure code free of unnecessary runtime-specific imports.
- Reuse SPT's existing TS domain/UI code. Selectively move pure spec validation, decision tables or packet/result-contract transformations only if the existing native/application consumer actually uses the result and the old semantic duplication can be removed.
- Keep thin Python at native credentials, plugin/session/scheduler and established process-lock/signal/recovery boundaries. Other Python HTTP/media/filesystem code is not inherently unportable, but no benefit currently warrants a wholesale port.
- Preserve SPT's npm/package-lock and canonical build/test contract. OCP's `bun@1.4.1` is its own owner decision; it does not migrate SPT automatically. The executable is `/opt/data/toolchains/bun/1.4.1/bin/bun`; bare PATH absence is not installation absence. Do not install another runtime or change global aliases for this plan.
- Keep workerd and Apps Script V8 as distinct deployed engines. TypeScript authoring, Bun execution and package management are separate choices. No direct Palantir/Bun compatibility claim follows.
- Use a portable same-behavior oracle before a selected migration, including deliberately broken input/behavior. The actual consumer and removal of duplication matter; an added TS schema/judge alone is not success.

No reusable "shared Bun contract runner" has been established by this review. The actual available assets are the pinned Bun executable, existing Project commands and the typed query implementation with its stated input limits. Do not invent an existing component or build a new runner just to satisfy that earlier phrase. A trivial settled TS/UI choice is not a reason to commission another language review or a paired-runtime benchmark.
