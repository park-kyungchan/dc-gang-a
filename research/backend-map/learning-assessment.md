## Candidate join graph

```text
student LMS key (stu_pri_no)
  ├── course assignment (course_seq / historical course ID)
  ├── lesson day record (date + grp_seq + record_seq + cm_seq)
  ├── preparation / DT-ZT / assessment result (student join still to verify)
  └── assessment attempt (ass_no + p_no + testing_no, exact cardinality unverified)
        └── paper item (lecture_key) ── official metadata / image / video
```

The DayRecord parser explicitly captures `course_seq`, `stu_pri_no`, `record_seq`, `cm_seq`: `ganga/lms/reader.py:268-296,349-404`. The local student DB uses `login_id` as `student_key` and caches those LMS keys, while its observations, progress, and item attempts are teacher-owned local records: `ganga/students.py:74-132,147-212,219-278`. Do not silently equate login ID, LMS primary number, group number, course ID, paper ID, and attempt ID. Establish a versioned mapping with source and last-seen time before joining data into one student view.

`src/mcp_server.py:192-256` returns hardcoded exam rows and item keys when its live query is empty. Consequently, that API's nonempty output is **not** proof of current academy state. Avoid using its fallback for acceptance or parent-facing claims. The same repository's `src/client.py:158-163` selects one of two textbook PDFs with a keyword heuristic, so that PDF link is not a verified per-student assignment.
